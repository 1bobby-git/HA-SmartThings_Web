# 조명·전원 제어 보완 — 1.8.20

## 확인한 근거

사용자 화면에는 1.8.19 조명 대기열 만료, 스위치 상태 확인 시간 초과, 공기청정기의 전원 제어 미발견 오류가 있습니다. 첨부된 Bridge 로그도 1.8.19이며 Web native 명령 접수 뒤 기기 상태 조회를 반복합니다. 이 로그에는 실패 기기의 정확한 속성·원본 상태값이 없으므로 모든 오류의 실환경 원인을 하나로 단정하지 않습니다. 원본 webarchive와 로그는 저장소에 포함하지 않습니다.

기존 소스에는 색상을 `setHue`→확인→`setSaturation` 순서로 전송하고, 객체 인수를 받는 `setColor`는 카탈로그에서 제외하는 구조가 있습니다. 첫 속성이 다음 명령과 함께 적용되는 기기에서는 뒤의 명령 자체가 전달되지 않을 수 있습니다. Home Assistant의 SmartThings 통합은 `setColor`에 hue/saturation 객체를 전달합니다. SmartThings 명령 요청은 같은 기기에 대한 여러 capability 명령을 배열로 받을 수 있습니다.

참고: [Home Assistant SmartThings 조명 구현](https://github.com/home-assistant/core/blob/dev/homeassistant/components/smartthings/light.py), [SmartThings 기기 제어](https://developer.smartthings.com/docs/devices/control-devices/).

## 변경

- 확인된 `setColor`는 hue/saturation을 함께 사용합니다. 평면 객체의 두 숫자 속성과 각 0~100 내 제한을 모두 검증합니다. 문자열 설명은 제거하고 객체·배열·참조·추가 검증 제약을 무시하지 않습니다.
- Bridge의 `lightPlanSupported`가 true이고 현재 카탈로그가 전원과 모든 요청 속성을 증명할 때만 같은 기기·컴포넌트의 2~4개 조명 명령을 단일 POST에 넣습니다. `applyLight`는 로컬 Bridge 내부 요청명이며 Samsung에 그대로 보내지 않습니다. 모든 인수 검사가 끝나기 전에 제어를 보내지 않습니다.
- POST 결과 전체가 접수되어도 성공 확정이 아닙니다. 실제 상태 이벤트 또는 전송 이후 시작한 정확한 기기의 상태 응답에서 요청한 결과 전체를 확인해야 합니다. 한 속성씩 기다리다가 다음 속성 전송이 막히지 않습니다. 한 항목이라도 거절되면 실패로 남기고 자동 재전송·롤백하지 않습니다.
- 조명에만 밝기/채도 0.5퍼센트포인트, hue 원형 거리 0.5퍼센트포인트, 색온도 역수 기준 1 mired의 제한된 일치 허용치를 둡니다. 예를 들어 밝기 요청 50에 실제 49.8이 보고되면 확인할 수 있지만 49는 실패합니다. HA에는 실제 값 49.8을 유지합니다. 채도 0의 흰색에서는 hue의 방향은 판정에 사용하지 않되 유효한 실제 두 상태가 있어야 합니다. 일반 센서/보안의 정확한 비교는 유지합니다.
- 일반 전원과 조명 숫자는 현재의 정확한 Advanced 명령·버전·안전 정책을 확인했을 때 직접 경로를 우선합니다. 명령이 없는 기기는 기존 Web 경로를 유지하고 다른 방/기기의 기능을 추측하지 않습니다. 캐시와 요청이 같은 전원도 실제 상태를 먼저 읽어 잘못된 `already_confirmed`를 방지합니다.
- 공기청정기 전원은 표시·읽기·실행 모두 같은 검증된 switch 항목을 사용합니다. action/detail 중복은 기존 공통 선택 규칙으로 처리하고 모호한 두 action이나 다른 컴포넌트는 임의로 선택하지 않습니다.
- 기존 시간 제한과 대기열 만료는 유지합니다. 요청을 실제 상태처럼 저장하거나, 실패를 성공으로 바꾸지 않습니다. 실행 중인 요청을 끊거나 불확실한 POST를 다른 전송 경로로 재전송하지 않습니다.

## 적용

Bridge 앱과 HACS 통합을 모두 **1.8.20**으로 업데이트하고 Bridge와 Home Assistant를 재시작합니다. 로그인 초기화, 통합/조명 삭제·재등록은 필요하지 않습니다. 엔티티 ID·방/재실·Home Monitor·Scene/TTS와 짧은 README를 유지합니다.

먼저 공기청정기 전원을 한 번 변경하고, 조명 밝기 50%와 다른 색상을 각각 한 번 적용해 실제 기기와 HA 값을 비교합니다. 문제가 남으면 `command_device:`의 기기 별칭·단계·일치 여부와 `command_route:`의 같은 시각 기록으로 구분할 수 있습니다. 진단에 원본 기기 이름, 계정정보, 쿠키, 토큰이나 실제 측정값은 추가하지 않습니다.

## 검증 범위

공유 합성 fixture로 원본 capability 정의→실제 카탈로그/저장소→HA 파서/조명 요청→실제 Advanced 어댑터의 POST 본문→상태 확인을 대조합니다. `setColor`만 구현된 가상 컨트롤러, 중간 단계 대기 제거, 지연·반올림 상태, 불완전한 응답·잘못된 대상·위치·범위, 캐시 불일치, POST 재전송 금지, 팬 중복 전원 선택을 검사합니다. 이는 사용자 전구/공기청정기를 실제로 조작한 기록이 아니며, 앱 전체의 연결 끊김 해결을 증명하지 않습니다.
