# 전구 Advanced 제어와 연속 조작 처리 — 1.8.25

## 수정한 구조

기존 HA 조명의 잠금과 Bridge의 기기별 FIFO는 명령을 전송한 후 최종 상태 확인까지 점유했습니다. 확인이 30초 걸리면 다음 요청은 10초 대기 한도를 먼저 소진하여 `command_queue_timeout`이 연속 발생할 수 있었습니다. 1.8.24의 비교/첫 조회 지연 수정은 이 구조를 바꾸지 않았습니다.

1.8.25의 새 경로는 **확인된 전구 + Bridge 기능 협상 + 명시적 `replacePending: true`**일 때만 사용됩니다. 기존 클라이언트·일반 기기·보안 명령은 기존 계약을 유지합니다.

```text
HA 첫 조작 → 전체 입력 검증 → Advanced 개별 POST → 실제 이벤트/대상 GET 확인
HA 연속 조작 → 75ms 병합 → 최신 요청
                    └ 이전 요청의 확인 대기/미전송 단계 중단
                    └ 이미 전송 중인 POST 완료 후 최신 요청 시작
```

각 Advanced 요청의 `commands`에는 실제 검증된 명령 한 개만 들어갑니다. 색상 `setColor`가 제공되면 hue/saturation을 그 명령으로 함께 전달합니다. 단일 `setHue`/`setSaturation`만 검증된 기기는 각각 전송하되 hue 확인이 saturation 전송을 막지 않습니다. 개별 명령 전송은 Advanced 개별 컨트롤과 같은 형태로 바꾸는 호환성 조치이며, 실제 안방 전구가 묶음 명령을 무시했다는 현장 측정 주장은 아닙니다.

## 실제 상태와 예외 처리

- HTTP 접수만으로 성공/켜짐/밝기/색상을 만들지 않습니다.
- 최신 요청의 네트워크/권한/오프라인/상태 확인 오류는 그대로 실패합니다. 명시적으로 대체된 요청만 별도 `command_superseded`로 종료합니다.
- 중간 단계가 실패하면 나머지 명령을 보내지 않습니다. 물리 명령을 임의로 반복하거나 이전 색상으로 롤백하지 않습니다.
- timestamp 누락/동일 보고는 두 번의 실제 대상 GET 일치, 기기·위치·컴포넌트 일치, 변경 없는 상태 revision이 모두 있어야 보정합니다. 새로운 조명 명령은 이전 read proof도 무효화합니다. 더 오래된 날짜의 응답은 거부합니다.
- 보정값에 `commandReadVerified`가 붙고 기존 upstream timestamp는 재생 방지 기준으로 보존됩니다. HA는 더 높은 인벤토리 sequence와 새 기능 협상까지 확인한 경우에만 동일 timestamp의 검증된 전구 값을 적용합니다. 요청값이나 현재 시각을 장치 timestamp로 조작하지 않습니다.

## 업데이트와 사용자 확인

Bridge 앱과 HACS 통합을 **둘 다 1.8.25**로 업데이트하고 재시작합니다. 기존 엔티티를 삭제하거나 재등록하지 않습니다. 이전 Bridge에서는 새 옵션을 보내지 않고 기존 경로를 사용합니다.

1. 안방 무드등을 켜고 밝기 20%→80%를 연속 선택하여 마지막 값 반영을 확인합니다.
2. 색상 빨강→파랑을 연속 선택하고 실제 전구와 HA 색상을 비교합니다.
3. 색온도 3000K→5000K와 끄기를 시도합니다. 이전 요청의 알림이 뒤늦게 쌓이거나 끈 후 이전 색상 명령이 이어서 켜지지 않아야 합니다.
4. 최신 요청이 실제 실패한 경우 Bridge 로그의 `command_device`에서 `lightStatus`의 `requested`/`observed`, 단계와 오류 코드를 확인합니다. 이것은 전구 값과 비식별 별칭만 포함합니다. 실제 계정 인증정보는 공유하지 않습니다.

## 검증 범위

명령 큐, 카탈로그/실제 Adapter/상태 저장소 연동, 느린 POST 중 교체, burst 병합, 입력 거부, 부분 실패, 날짜 보호, HA 클라이언트/엔티티를 회귀 테스트합니다. 기존 Home Monitor 단위/Chromium 검증도 그대로 실행합니다. 저장소 CI 및 릴리스 공개와 사용자 HA 실제 설치/물리 작동은 서로 다른 검증 단계입니다.
