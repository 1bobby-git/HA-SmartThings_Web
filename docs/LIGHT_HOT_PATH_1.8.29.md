# 조명 연속 조작의 추가 대기 감소 — 1.8.29

## 변경 범위
기준 1.8.28(277a19390ec4775609f57a23c55638608a3eee97). 사용자가 제공한 1.8.27 로그에서 POST 접수까지 811~864ms(전원), 2638ms(세 명령)가 걸렸다. 1.8.28 이후의 실기기 상세 타이밍은 없으므로 남은 지연 원인이나 개선율을 확정하지 않는다.

## 개선
직전 **성공한** 조명 명령의 접수 이후 읽은, 전체 목표와 일치하는 정확한 대상 GET만 일회성 증거로 보관한다. 원래 조회 시작 시각부터 최대 1000ms이며 재사용으로 만료가 연장되지 않는다. state revision, 기기/위치, keeper 객체, 재연결/상태 전환 epoch가 같아야 사용한다. 최근 읽기가 없거나 만료되면 1.8.28의 새 GET 검증을 그대로 사용한다. 캡처되는 상태는 복사본이며 저장소에 게시하지 않는다. 성공하지 않은 명령, 늦게 도착한 이전 세대의 읽기, 일반 명령이나 scene/location 명령을 건너뛰어 재사용하지 않는다. 최대 128개 항목이며 디스크 저장/상시 타이머가 없다.

사전 조회 실패/시간초과에는 5000ms의 optional-preview backoff를 둔다. 이 동안 명령 처리는 즉시 기존 전체 순서로 실행한다. 최근 유효 증거가 있으면 새 GET 없이 검증 후 중복 명령을 줄일 수 있다. 취소를 실패로 세지 않는다. POST 자동 재전송/병렬화/묶음 전송을 추가하지 않는다.

전원 단독과 색상/색온도 setter는 생략하지 않는다. 생략된 전원/밝기를 포함한 모든 목표를 명령 이후 확인한다. 성공 응답을 빠르게 만들기 위해 요청값을 상태로 게시하거나 확인 조건을 완화하지 않는다. 외부 물리 변경이 아직 관측되지 않은 짧은 경합 가능성은 기존 GET 직후에도 존재하며, 이 경우 목표 미일치는 계속 실제 실패로 처리한다.

## 진단
- command_device.preflightSource=recent_read: 직전 성공한 실제 읽기를 재사용; preflightMs=0.
- live_read: 새 사전 GET. backoff: 실패한 선택 조회를 반복하지 않고 기존 명령을 바로 전송.
- advanced_request_timing: 개별 Advanced commands POST의 route, totalMs, browserMs, fetchMs, bodyMs, bridgeOverheadMs, status.
- fetchMs는 페이지 fetch 시작부터 응답 헤더 반환까지이며 브라우저 요청 대기·네트워크·서버 응답이 합쳐진 값이다. bodyMs는 JSON 본문 수신과 파싱, bridgeOverheadMs는 관측된 페이지 내부 시간 외의 평가/통신 부가 시간이다. 이 수치는 물리 전구 완료나 HA 렌더링 시간이 아니다. 비정상 숫자는 생략하고 진단 콜백 실패가 명령을 실패시키지 않는다.

## 검증
합성 800ms POST/100ms 사전 GET에서 첫 조작 901ms, 직후 두 번째 801ms로 검증한다. 최근 읽기를 사용한 무반응 색상은 여전히 timeout이며 재연결/만료/이전 세대/단독 전원/비활성 설정/잘못된 읽기 검사를 포함한다. 사용자 전구 실측 개선 수치는 아니다.

실제 Chromium의 전송 함수도 모든 네트워크를 가로채는 fixture로 검사한다. CSRF와 원래 payload, 403 거부/재전송 금지, 숫자 진단과 개인정보 미출력을 검증한다. 삼성 계정이나 실제 기기를 제어하는 테스트가 아니다. 기존 Home Monitor Chromium·HAOS 시작·보안 검사 게이트는 그대로 통과해야 릴리스한다.
