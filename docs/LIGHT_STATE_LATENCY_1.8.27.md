# 조명 상태 전달 지연 개선 — 1.8.27

## 범위
1.8.26에서 사용자 dev_300의 setColor가 등록되고, 오류 없이 실제 상태가 맞게 표시된다는 보고 이후의 지연 개선이다. 정상 동작하는 색상 명령의 전송 방식이나 Home Monitor의 제어/확인 방식은 바꾸지 않는다. 실제 사용자 HA나 전구의 제어 시간을 원격 측정한 결과는 아니다.

## 제거한 대기 경로
기존 조명 명령의 대상 GET에서 값이 바뀌면 inventory 마커가 발행되고 HA가 전체 기기 목록을 다시 GET했다. 이제 deviceId/locationId/status만 있는 정확한 응답이며, 모든 상태 키/역할/단위가 기존 등록 정보와 일치하면 변경 상태만 전달한다. metadata, 새로운 상태 키, 등록 정보 변경은 전체 인벤토리 경로를 유지한다. 일반 조회와 Home Monitor에는 이 최적화를 적용하지 않는다.

전달하는 것은 원래 GET의 관측값이며 `source: COMMAND_STATUS_RECHECK`와 timestamp를 보존한다. Samsung push의 eventTime/commandId를 만들지 않는다. 동일 timestamp 값 보정은 기존대로 두 번의 독립 GET 일치와 중간 이벤트/새 명령이 없다는 검증을 거친 값만 적용한다. HA도 해당 출처/기능 협상/조명 속성/sequence와 timestamp 조건을 검사한다. sequence가 빠지거나 재연결됐으면 기존 전체 동기화를 수행한다.

## 명령 직후 조회 일정
상태 재확인이 켜진 조명에만 적용한다. 시작점은 모든 전송이 접수된 이후이며, 각 READ는 직렬이고 이전 READ 종료 후 최소 250ms를 둔다. 30초 제한의 확인 회차는 8회로 동일하다. 변경이 확인되거나 명령이 대체/취소되면 남은 예약을 제거한다. 기기 timestamp가 불완전한 경우의 두 번 조회는 기존과 같다.

| 접수 후 예약 시각(ms) | 기존 | 변경 |
|---|---|---|
| 조회 일정 | 250, 1250, 3250, 6250, 9250, 14250, 19250, 25000 | 0, 500, 1250, 2500, 4500, 8000, 14000, 25000 |

재확인이 꺼진 경우에는 기존과 같이 마지막 확인만 수행한다. 네트워크/기기 지연을 없앤다는 의미가 아니며, 백그라운드 상시 고속 폴링도 아니다.

## 재현 검증
실제 scheduler 두 개를 가상 시계로 실행하며 네트워크 왕복을 제외한 합성 예제이다. 사용자 안방 전구의 실측 수치가 아니다.

| 합성 상태가 준비되는 시점 | 기존 발견 시점 | 변경 발견 시점 |
|---|---|---|
| 300ms | 1250ms | 500ms |
| 2000ms | 3250ms | 2500ms |
| 4000ms | 6250ms | 4500ms |

229개 장치의 Python 회귀 fixture에서 기존 전구 값의 직접 상태 전달은 전체 인벤토리 GET 없이 대상 리스너만 갱신한다. 순서 누락이면 여전히 GET한다. 실제 조명 Entity 격리 테스트에서는 명령 HTTP 응답이 아직 대기 중이어도 관측된 전원/색상/채도가 반영되고, 마지막 sequence를 이미 받으면 추가 전체 조회를 하지 않는 것을 검사한다.

회귀 검사는 이전 날짜/출처/미검증 값 거부, 같은 날짜 두 채널의 연속 전달, 중간 새 명령에 의한 무효화, 메타데이터/새 상태의 인벤토리 fallback, READ 직렬화, 최대 회차, 취소, 일반 제어/Home Monitor의 기존 검증도 포함한다.

## 운영 확인
Bridge와 HACS 통합을 함께 업데이트한다. command_device의 dispatch → receipt 간격은 명령 전송 접수 구간이고, readMs는 실제 대상 조회 구간이며, confirmed의 elapsedMs는 Bridge 내부 제어 시작부터 확인까지이다. 이 숫자는 HA 화면 렌더링 완료 시각이 아니다. 제어 후 실제 밝기/색온도/색상과 HA를 비교해야 하며, 이 변경만으로 모든 네트워크/기기 지연이 해소됐다고 단정하지 않는다.
